# Releasing watergate-local-api-python

This repository is a **library**: a release is a version tag and a GitHub Release. There is nothing to deploy and no production approval. This page is generated by `release-init` from `.github/release-config.yml`; the part above the end marker is rewritten when you re-run it, so put repository-specific notes below the marker. Details: [release-workflows docs](https://github.com/watergate-ai/release-workflows/tree/main/docs).

## Overview

- **Versions** are CalVer `YYYY.N.P`, tags `vYYYY.N.P`. `N` counts the releases of the year, `P` the hotfixes of that release. Consumers pin a tag and read the changelog (CalVer carries no compatibility signal).
- **There is no version file.** A release is `YYYY.(N+1).0`, counted from the highest `vYYYY.*` tag of the year (`YYYY.1.0` on the first release of a year).
- The GitHub Release is published immediately (not a pre-release). A repository workflow listening to `release: published` may publish the package (for example to PyPI): it fires because Release creates the GitHub Release with the release-bot App token.

## Release

1. Check that the tests of `main` are green.
2. Optional: **Actions -> Release** with `dry-run: true` and read the plan.
3. **Actions -> Release -> Run workflow** from `main` ("Use workflow from"): `type: release`, `ref` empty. Release tags exactly the commit its tests ran on, so it must be started from the branch it releases.

## Hotfix

```sh
git fetch --tags
git switch -c hotfix/<short-description> v<last released version>
# commit the fix, open a PR into this branch, merge it
```

**Actions -> Release** with `type: hotfix`, started from that branch (leave `ref` empty). Release tags `vYYYY.N.(P+1)` and opens a back-port PR into `main` that a person merges.

## Rollback

Consumers pin tags, so a bad release is rolled back by consumers pinning the previous tag. Release a fixed version (or a hotfix); do not delete tags or GitHub Releases.

## Re-running after a failure

Run **Release** again with the same inputs: an existing tag on the same commit, the GitHub Release and the Confluence page are reused or updated; a tag on another commit stops the run with a message and changes nothing.

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| Release stops: *tag vX already exists on another commit* | That version was cut from other code: bump or release the next version. Nothing was changed |
| The `test` job fails or is a stub | `.github/workflows/test.yml` is the repository's own; see `docs/test-workflow-contract.md` in release-workflows |
| *release-config.yml: ...* | The message names the key; fix `.github/release-config.yml` (`release-init --check` shows the same) |
| The package is not published | The publishing workflow listens to `release: published`; check that it ran and that the release was created by the release bot |

## Repo-specific notes

### Publishing to PyPI

- `.github/workflows/publish-pypi.yml` (formerly `release.yml`) builds, tests and publishes to PyPI with Trusted Publishing (OIDC) when a GitHub Release is **published**. It is not part of the shared flow and is unchanged apart from its name and a comment. The package version is the release tag name (setuptools-scm strips the `v`): `v2026.3.0` publishes `2026.3.0`.
- It only fires because Release creates the GitHub Release with the release-bot App token (events from `GITHUB_TOKEN` do not start workflows). If a release shows no `Release` run of `publish-pypi.yml`, the release was created with another token: see Troubleshooting.
- PyPI never accepts the same version twice, so a failed publish is repaired by re-running that workflow run, not by re-cutting the tag.

### The first release under this flow

Tags before this flow have no `v` (`2026.2.2` is in production on PyPI and is the latest GitHub Release). The shared version logic only counts `vYYYY.*` tags, so on a repository with none it would compute `2026.1.0`, which PyPI already has. **Run the first Release with `override-version: 2026.3.0`** (the next number after `2026.2.2`); later releases are computed from the `v` tags it creates. Do not create `v` aliases of the old tags.

Until the first release under this flow exists, there is no `v` tag, so a hotfix cannot be computed; a hotfix of `2026.2.2` is out of scope (cut a normal release).

### Branch protection

The ruleset `Master protection` requires one approving review on `main`. Release never pushes to `main` and, for a library with `version.source: tag`, opens no bump PR, so no bot PR waits for a review.
